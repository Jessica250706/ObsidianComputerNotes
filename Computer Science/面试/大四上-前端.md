## 2. 重点：讲下 STable 可拖拽表格组件，你独立封装重构，具体实现思路是什么？

> 表格支持搜索、排序、筛选、拖拽、跨页选择，跨页选择状态你是怎么保存的？遇到组件数据流传递混乱，这个问题具体是什么现象？根因是什么？你怎么解决？表单清空逻辑异常，什么场景会清空失败？是组件内部状态没重置还是父组件传参问题？组件是基于 Ant Design Vue 二次封装还是完全自己写？props、emit 怎么设计，如何保证多业务场景复用？简历写复用后减少约 30%重复模板代码，这个数据是怎么评估出来的？

STable 是**基于 Ant Design Vue a‑table 做二次封装的业务通用表格组件**，不是从零手写 DOM 表格。 项目原生 JeecgBoot 提供 `BasicTable` 以及 `useListPage` 钩子，但原生钩子存在局限：无法完整控制筛选、排序清空逻辑，很多业务页面重复写搜索栏、分页、多选、拖拽样板代码，所以我进行封装重构。

### 整体实现思路

1. 将搜索表单、表格主体、分页收拢到组件内部，通过 props 传入列配置、请求函数、主键标识、功能开关；
2. 内置搜索、重置、分页；行拖拽基于第三方拖拽库实现，拖拽事件对外抛出；
3. 增强多选，实现跨页勾选；业务页面只传配置，特殊业务场景通过插槽扩展；
    
    > 踩坑背景：开发中途发现 vxe-table 本身自带拖拽，但业务已经基于 a‑table 推进，因此继续基于 antdv 封装；责任人、责任部门、时间多选筛选能力，组件侧逻辑完成，**筛选数据源依赖后端接口支持**。
    
1. 重构关键点：放弃 JeecgBoot 原生 `useListPage` 钩子，改为受控模式接管筛选、排序、清空逻辑，解决原生钩子无法重置筛选状态的 BUG。

### 跨页选择状态如何保存

组件内部维护 `selectedRowSet` 集合，存储业务唯一主键以及完整行对象，**不用单纯依赖页面当前渲染数据**。

- 翻页不会清空集合；渲染每一行时，根据 Set 中的 ID 回显复选框勾选；
- 删除、取消勾选、清空操作操作该集合；通过 emit 事件向外抛出完整选中集合；
- props 约定传入 `primaryKey`，指定业务主键字段，规避主键字段不一致问题。

### 数据流传递混乱：现象、根因、解决方案

**现象**：多个业务页面复用 STable，切换弹窗、切换页面时，表格内部筛选条件、勾选状态发生互相污染；父组件更新查询条件、外部选中集合，组件内部状态没有同步，视图和数据不一致。

**根因**

1. 早期直接将 props 查询对象直接赋值给组件内部响应式变量，属于引用赋值，父子状态双向耦合，组件内部修改会污染父源对象；
2. 仅在组件挂载时监听一次外部传入的初始选中集合；父组件后续修改选中集合，watch 不会再次触发回显。

**解决**

1. props 传入的查询参数，组件内部做深拷贝生成本地副本，组件只操作副本，严格遵循单向数据流，不直接修改 props；
2. 对外部传入的 `initSelected` 开启深度监听，外部选中集合变更同步更新内部 `selectedRowSet`；
3. 组件内部所有状态变更，全部通过 emit 通知父组件，组件不直接修改父组件数据。

### 表单清空逻辑异常场景与根因

**场景**：弹窗使用 v‑show 复用 STable 组件，关闭弹窗再重新打开，表格筛选条件、勾选状态依旧残留旧数据。

> 根因：**组件实例没有销毁，内部 Set 集合、筛选表单状态保留，并不是父组件传参问题**。

修复：组件对外暴露 `clear()` 实例方法；父组件在弹窗关闭时通过 ref 调用该方法，清空选中集合、重置筛选表单、重置页码。

### props、emit 设计，保障多业务场景复用

**Props**

- 基础：`columns` 列配置、`api` 请求函数、`primaryKey` 主键、`pageSize`；
- 功能开关：`isSearch`、`isDrag`、`isMultiple` 控制搜索、拖拽、多选；拖拽开启时会屏蔽部分筛选排序能力；
- 外部初始数据：`initSelected` 外部初始选中集合，`initQuery` 初始查询条件。

**Emit**：`search` 搜索触发、`drag‑end` 拖拽完成、`change‑select` 选中变更、`page‑change` 分页切换。

同时预留多组插槽：搜索前置插槽、单元格插槽、底部插槽，通用逻辑内置，差异化业务交给插槽扩展，兼顾通用性和业务定制。

### 减少 30%重复代码评估方式

重构前统计市场管理模块 3 处使用表格的业务页面，统计搜索栏、分页、多选、拖拽相关模板与 JS 逻辑行数； 重构后同等业务，页面只需要配置 props，统计业务代码行数。 `(重构前总代码行数‑重构后总代码行数) ÷ 重构前总代码行数`，取多个页面的平均，得到约 30%，主要消除大量样板重复代码。

> 补充：组件本身代码量增加，但业务页面的重复样板代码大幅降低。

## 4. 使用 JeecgBoot 平台开发，说说 JeecgBoot 的开发模式，它的低代码是怎么和 Vue 3 结合的？你觉得 JeecgBoot 有哪些优缺点？

JeecgBoot 是企业级低代码脚手架，后端 SpringBoot，前端 Jeecg‑Vue 3 基于 Vue 3+Ant Design Vue。

### 两种开发模式

1. **Online 在线低代码模式**：可视化配置表单、列表，生成 JSON Schema，无需手写页面代码，适合简单 CRUD；
2. **代码生成器模式**：配置数据表，一键生成 Vue 页面、Controller、Service、Mapper 基础模板，开发人员在生成代码基础上做业务改造；我实习项目主要使用第二种模式。

### 和 Vue 3 如何结合

Jeecg‑Vue 3 本身就是 Vue 3 工程。

1. Online 模式：后端输出 JSON 配置，前端运行时解析 JSON Schema 动态渲染 Vue 组件；
2. 代码生成器：直接输出 Vue 3 单文件 SFC，我们在生成代码上手写业务；
3. 框架内置封装：全局字典解析、权限 `v‑permission` 指令、统一请求封装、vxe‑table、UnoCSS 等；底层完全复用 Vue 3 响应式、组件系统。

### 优点

1. CRUD 业务开发效率高，代码生成器省去基础增删改查工作量；
2. 内置完整权限、租户、字典、登录体系，不用从零搭建后台骨架；
3. 开箱即用大量业务基础组件。

### 缺点（结合我实际踩坑）

1. 自动生成样板代码，业务复杂时定制改动成本高；
2. 部分底层逻辑黑盒，原生钩子存在局限，遇到 BUG 需要阅读源码调试，例如 `useListPage` 筛选清空问题；
3. Online 低代码 JSON 模式灵活性有限，复杂交互必须手写 Vue；
4. 项目如果缺少版本管控，底层模板大规模变更，会导致已写页面需要大面积重构，我实习期间就遇到底层模板更新，大量页面传参、组件衔接逻辑要全部修改，部分前期代码失效。

> 实际场景：CRM 业务交互复杂，我没有大量使用 online 低代码，主要靠代码生成器生成基础模板，再手写改造页面、封装业务组件。

## 5. 遇到 BUG：弹窗选中数据不回显、ID 冲突造成数据清空，复现步骤是什么？定位 BUG 的排查思路，最后如何修复？

### 复现步骤

1. 打开活动总结选择弹窗，勾选活动记录，确认回填表单；
2. 再次打开弹窗，弹窗内部没有回显上一轮选中数据；
3. 最开始直接传递 id，活动记录 id 与其他业务 id 存在数值重复，Set 集合 key 冲突，选中数据被错误清空。

### 排查思路

1. 第一步看确认事件返回值，确认父组件拿到的选中数据本身正确；
2. 打印 props 传入弹窗组件的 `initSelected`，确认父组件数据没问题；
3. 调试 watch 监听，发现 watch 仅在组件 onMounted 执行一次；弹窗通过 v‑show 复用，组件实例不会销毁重建，再次打开弹窗，props 更新 watch 不会触发回显逻辑；
4. ID 冲突：组件内部 Set 直接用 id 数字作为 key，不同业务对象 ID 数值重复，发生覆盖丢失选中项。

### 修复方案

1. 弹窗回显：给 `initSelected` 开启深度 watch 监听；弹窗打开的时候主动执行一次回显逻辑，不依赖组件挂载；
2. ID 冲突：最开始临时改用业务名称 `huodongmc` 传递规避冲突；长远方案是组合 key（`type‑id`）区分不同业务对象，同时完整保存行对象，不只存 id。

## 7. 前端开发遇到需要后端排期，你选择自己写简单接口，那什么场景适合前端自己写简单接口，什么场景不建议？前后端职责边界你怎么理解？

### 适合我来写简单接口场景

1. **单表简单 CRUD，无复杂事务逻辑**；
2. 仅服务当前业务模块，不会被其他多个服务、多个页面复用；
3. 后端排期紧张，会阻塞前端开发进度，写接口用来解耦开发节奏；
4. 业务规则简单，没有权限、资金、复杂计算。

### 不适合前端写接口场景

1. 需要多表更新、数据库事务保证原子性；
2. 核心业务数据，涉及权限校验、金额、客户核心信息；
3. 接口会被多个业务、多个服务调用，需要统一维护；
4. 业务规则复杂，大量计算逻辑。

### 前后端职责边界理解

1. **后端职责**：数据持久化、数据库设计、权限校验、事务、复杂业务规则；**无论前端是否做过校验，后端必须做二次参数校验，绝对不信任前端传参**。我写的接口写完之后，也会同步给到后端同事，后续迭代交给后端维护，不作为长期由前端维护的方案。
2. **前端职责**：页面交互、组件封装、体验层表单校验、接口联调；前端表单校验只用于提升用户体验，不能作为安全屏障。
3. 我写后端接口，更多是为了解决排期阻塞，属于阶段性临时方案，不是把核心业务交给前端开发。

### BUG 定位整体流程

1. 稳定复现 BUG，整理复现步骤；
2. 判断问题归属：区分接口问题、JS 逻辑问题、渲染问题、样式问题；

6. **Application**：查看 localStorage、sessionStorage 本地存储，排查本地存储相关问题。

# 四、第二份实习：浙江君同智能科技（Vue 3 + React 双栈，AI 教学实训平台、后台管理）

> 简历关键点：Vue 3 页面解决大批量数据渲染卡顿；React+Umi+Ant Design Pro 开发模块；文件预览 docx/xlsx；:deep()样式穿透；封装 hooks/utils；Markdown 图片上传自动携带 token；Git 多人协作、5+版本迭代

> 背景说明：2025.07‑2025.09 实习，并行维护两个项目：**Vue 3+Element‑Plus+TailwindCSS 君学人工智能治理教学实训平台（君教）**、**React+TS+UmiJS+Ant Design Pro 君同未来官网后管系统**；参与 5+版本迭代，包含需求评审会议、页面开发、组件封装、样式兼容、缺陷修复、前后端联调、Git 多人协作；部分开发会先基于静态 UI 稿开发，后续对接接口，部分需求无完整 PRD，需要和产品、UI 持续对齐逻辑与样式。

## 1. 两个项目分别是做什么？同时接触 Vue 3 和 React，讲讲两者开发体验的差异？

**君学人工智能治理教学实训平台（Vue 3）**：面向高校老师、学生的 AI 实训教学平台。教师侧可以创建实验、发布考试、批阅学生提交的实训作业；学生完成实验实训、提交作业。我负责**实验控制台、批阅情况、考试管理**三大模块。实验控制台主要用来管理虚拟机实训实例，做虚拟机启停、批量操作、资源占用可视化；批阅情况用来查看学生实验/考试提交状态、批阅作业；考试管理实现考试创建、分步表单、发布管理。

**君同未来官网后管系统（React+UmiJS+Ant Design Pro）**：企业后台管理系统，用来维护官网对外展示内容，包含**企业动态管理、资源中心管理、生态伙伴管理**。可以完成新闻动态发布上下架、各类附件资源上传、docx/xlsx 文件预览、合作伙伴信息维护，数据最终会渲染到对外官网页面。

### Vue 3 组合式 API vs React hooks 开发体验差异

1. **响应式机制不一样**：Vue 3 基于 Proxy，模板和脚本分离，template 模板语法，ref/reactive 自动收集依赖，修改变量就自动更新视图；React 是**状态不可变**，必须通过 setState、useState 返回的更新函数触发重渲染，直接修改对象不会生效，这点刚切换 React 踩过不少坑。
2. **代码组织**：Vue 3 setup 语法糖，模板、脚本、样式写在同一个 SFC 单文件；React 是 JSX，HTML 写在 JS 里面，逻辑和标签写在一块，组件就是 tsx 函数。
3. **副作用处理**：Vue 3 用 `watch/watchEffect`；React 使用 `useEffect`，需要手动维护依赖数组，依赖漏写会产生闭包陷阱，这是我开发中重点注意的点。
4. **生态组件**：Element Plus、Ant Design Vue 是 Vue 生态；Ant Design Pro 是 React 中后台完整脚手架，内置路由、权限、请求、ProForm 高阶表单，开箱即用能力很强。
5. **TS 体验**：两者都支持 TS；React 写 TSX 对类型推导要求更高；Vue 3+TS 配合 defineProps 也可以做强类型约束。

> 实际工作：我是先做 Vue 项目，中途接手 React 项目，一边看文档一边做业务，慢慢适应不可变状态与 useEffect 依赖数组的规则。

## 2. Vue 3 项目里面大批量数据渲染卡顿，当时是什么场景？虚拟机管控页面数据量大概多少条？你做了哪些优化？虚拟列表有没有考虑过？

**场景**：实验控制台页面，展示虚拟机卡片列表，老师班级学生数量多的时候，一次性渲染几十条虚拟机 card 卡片，包含资源 ECharts 小图表、多种状态标签、批量操作按钮，页面滚动、批量勾选操作出现卡顿。数据量一般单页几十条，极端场景可以到 80‑100 条。

我做的优化手段：

1. **分页加载**，不一次性拉取全部数据，后端做分页接口，前端控制每页展示条数，减少一次性 DOM 节点数量；
2. **状态节流**：批量全选/反选操作，减少高频触发组件重渲染；
3. **ECharts 图表实例管理**：组件销毁时销毁图表实例，防止内存持续堆积；
4. DOM 层面：实验名称文本超长使用 `truncate` 文本截断，**父容器必须设置固定宽度**，否则 ellipsis 省略号不生效，开发中踩过这个坑。

虚拟列表：我当时评估过，虚拟列表适合上千条以上长列表。本项目业务最多百条级别，分页+上面优化已经满足性能，所以没有引入虚拟列表；但我清楚虚拟列表原理，如果后续数据量级上涨会优先采用虚拟列表。

> 补充业务细节：页面要支持**跨页全选**，全选的时候不是选中当前页面，要标记全部查询条件下数据 id 集合，而非仅当前页行，这块逻辑做过处理。

## 3. 讲下 React 这边 UmiJS、Ant Design Pro 开发，Umi 的约定式路由你怎么理解？

Ant Design Pro 是基于 UmiJS 构建的中后台脚手架。

- **UmiJS**：企业级 React 框架，内置路由、构建、mock、代理、请求封装。分为**配置式路由**和**约定式路由**。
- **约定式路由**：根据 `pages` 目录下文件/文件夹目录结构自动生成路由，不用手动在路由配置里一条条写 path；文件即路由，index.tsx 代表文件夹默认页面。
    
    > 但是约定式路由有风险：约定式路由**不会自动做权限控制**，直接输入 URL 可以绕过菜单访问页面，需要手动增加权限校验。
    

我项目同时两种模式混用：普通业务页面使用约定式路由；**文件预览页面 docx/xlsx，使用配置式路由，设置 `layout:false` **，去掉后台侧边栏、导航栏，实现单独全屏预览窗口，就是配置路由完成的。

Ant Design Pro 在 Umi 之上封装了 ProTable、ProFormUploadButton 等高阶组件，表单、表格样板代码大幅减少，同时封装了 request 请求、权限、错误处理。

## 4. 你实现 docx、xlsx 文件预览，用了什么库？简单讲下实现流程，大文件预览会有什么问题？怎么处理？

我使用 `@js‑preview/docx`、`@js‑preview/excel` 做浏览器端本地解析预览，不需要后端转 PDF。

**实现流程**

1. 在 Umi 配置路由，新增预览路由，设置 `layout:false`，脱离后台布局；路由携带文件 uuid 参数；
2. 新建独立预览组件 `DocxPreviewWindow.tsx`、`XlsxPreviewWindow.tsx`；
3. 通过路由拿到 uuid，调用后端下载接口，带上 token 鉴权，拿到文件二进制 Blob；
4. 将 Blob 传入预览库，挂载到指定 DOM 容器渲染文档内容。
5. 资源中心页面点击预览按钮，通过 `history.push` 跳转到预览路由，把文件 uuid 传过去，新开独立页面预览。

**遇到的问题**

1. **鉴权问题**：文件下载接口需要 token，直接 a 标签打开无法携带 token，所以不能直接 href 下载，必须前端请求拿 blob 再交给预览库。
2. **大文件性能**：库在浏览器内存解析整个文档，docx/xlsx 过大（几 MB 以上）会占用大量内存，页面卡顿甚至浏览器崩溃。 **处理策略**：前端增加文件大小判断，超过阈值给出提示，不使用前端预览，引导用户下载到本地打开；
3. 部分复杂 office 样式、合并单元格、特殊图表解析会有兼容性差异，属于第三方库本身限制。

另外上传组件使用 ProFormUploadButton，重写 `customRequest` 自定义上传逻辑，处理图片/附件上传、删除、记录待删除文件列表，提交表单时一并传给后端。

## 5. 使用 `:deep()` 样式穿透修复 el‑dropdown、el‑tabs 样式冲突。讲讲 `:deep()` 原理，Vue 3 里面深度选择器有几种写法？什么情况下第三方组件样式被全局覆盖？除了 deep 还有哪些解决方案？

### :deep()原理

Vue 单文件组件 `<style scoped>`，编译时会给组件 DOM 增加唯一 data‑v‑xxx 属性，CSS 选择器带上这个属性实现样式隔离，只作用当前组件。 第三方组件（el‑dropdown、el‑tabs）生成的 DOM 是挂载到组件外部，不会带上当前组件的 data‑v 属性，scoped 样式无法命中子组件 DOM。 `:deep(选择器)` 告诉编译器，把括号内选择器**去掉 data‑v 哈希属性**，就可以穿透 scoped，修改子组件内部 DOM 样式。

### Vue 3 scoped 深度选择器三种写法

1. `:deep(.selector)` 推荐（Vue 3 标准写法）
2. `/deep/ .selector`（已废弃，仅兼容旧项目）
3. `::v‑deep(.selector)`（废弃）

### 什么场景出现第三方组件样式被全局覆盖

1. 写了不带 scoped 的全局样式，权重过高，污染第三方组件；
2. 多个业务组件都使用 deep 修改同一个组件，样式互相覆盖；
3. TailwindCSS 全局原子类污染第三方组件内部 DOM。

### 其他解决方案

1. 去掉 scoped，但是会变成全局样式，要加外层类名做命名空间，防止污染；
2. 给第三方组件增加自定义 className，基于这个 class 写自定义样式；
3. 动态 style 行内样式（适合简单样式，复杂 css 不推荐）；
4. CSS Module。

> 我实习真实场景：实验控制台页面，需要修改 el‑dropdown 下拉弹窗背景、阴影、hover 激活态；el‑tabs 标签页字体、下划线样式，弹窗 DOM 挂载在 body 下，scoped 直接写不生效，使用:deep()完成自定义 UI，同时为了防止全局污染，外层增加业务 class 限定作用域。

## 6. TS 抽离 hooks 与 utils，index.ts 统一导出。讲讲自定义 hooks 设计原则，举一个你实习写的自定义 hooks 例子。

### 自定义 hooks 设计原则（React）

1. **单一职责**：一个 hook 只做一件事，不要把多个无关逻辑塞到同一个 hook；
2. 输入输出清晰，类型完整，入参、返回值全部定义 TS 类型；
3. 内部状态隔离，多次调用互不干扰；
4. 尽量把副作用封装在 hook 内部，外部组件只消费返回的数据和方法；
5. 注意依赖数组，避免闭包陷阱；组件卸载要清除定时器、事件监听、请求 abort，防止内存泄漏。

### 我写过的 hooks 示例（官网后管 React 项目）

1. `useFileUpload.ts`：封装文件上传通用逻辑，处理文件大小、格式校验、customRequest、待删除文件收集，上传成功回调，多个表单页面复用。
2. `useFormValidation.ts`：封装表单校验的公共逻辑。

utils 目录下把通用工具函数，文件处理、markdown 图片处理，全部抽离，通过 `index.ts` 统一 export 导出，业务页面只需要一次 import。

> 收益：企业动态、资源中心、生态伙伴多个模块复用，消除重复代码，简历写的减少约 30%重复代码是统计多个业务页面样板代码行数对比得到。

## 7. 覆写 Markdown 图片上传预览，实现图片请求自动携带 Token。图片请求为什么不会带上 token？你是在哪里拦截处理？遇到哪些坑？

### 背景

后台使用 markdown 编辑器，编辑器自带图片上传组件，但是图片预览、上传请求不会自动带上登录 token，后端鉴权拦截返回 401。 普通 axios/umi‑request 拦截器只能拦截我们自己代码发起的请求，**markdown 编辑器内部封装的图片请求是编辑器库内部直接发起 fetch/xmlHttpRequest，不会走项目封装的 request 实例，拦截器拦截不到，因此不带 token**。

### 处理方案

1. 不直接使用编辑器内置图片上传组件；覆写 markdown 的图片上传与预览组件，抽离 `uploadImage.ts`、`preview.tsx`；
2. 上传：图片上传请求直接使用项目封装好的 umi‑request 实例，自动带上 requestInterceptors，附带 token；
3. 预览：图片资源地址返回 uuid，请求图片二进制接口，使用项目 request 带上 token 拿到 blob，再传给 markdown 渲染。

### 踩过的坑

1. 直接修改第三方库源码不可维护，所以做组件覆写，在业务层替换编辑器内置图片部件，不改动 node_modules；
2. 图片上传完成后编辑器回显时机问题，需要等待接口返回再渲染图片标签；
3. blob 预览内存释放，组件卸载清理预览资源，避免内存占用。

## 8. 使用 Git 完成分支管理、代码冲突处理与合并，参与 5+版本迭代。讲讲你们团队 Git 工作流？遇到复杂代码冲突，你的处理步骤？怎么减少后续冲突？

### 团队 Git 工作流

- `main`：保护主分支，存放线上稳定版本，禁止直接 push；
- `feature/v1.3.0、feature/v1.4.0`：版本特性分支，我们日常开发全部基于版本 feature 分支；
- 每个人从 feature 分支切自己本地开发分支，开发完成后提交 PR/MR，合并回对应版本分支；
- 测试修复 bug 直接在 feature 分支；版本测试通过合并到 main。

### 复杂冲突处理步骤

1. 开发前先拉取远端最新 feature 分支，本地同步代码；
2. 出现冲突，优先看 IDE（VSCode）的冲突可视化工具；**优先看懂两边变更语义，不能无脑保留一边**；
3. 区分：自己新增代码、同事修改的原有代码，判断业务逻辑，和相关开发同学确认冲突部分业务意图；
4. 解决完冲突，编译项目跑通，确认页面功能正常，再 add、commit；
5. 不要把编译产物、dist、node_modules 提交。

### 如何减少冲突

1. 模块拆分，组件、业务逻辑尽量拆分文件，不要单个 tsx 几千行大文件（实习遇到 1200 行未拆分组件，冲突概率极高）；
2. 及时同步远端分支，不要隔很久才合并；
3. 公共组件、公共 hooks 尽量抽离，业务页面少改公共文件；
4. 多人开发同一个页面，提前简单沟通开发范围。

> 实习实际情况：并行两个项目多版本迭代，经常处理冲突；有历史遗留超大未拆分组件，修改的时候冲突非常痛苦，也意识到组件拆分的重要性。

## 9. 两份实习都做组件封装，对比两份实习封装的组件，哪些是业务组件、哪些是通用基础组件，区分标准是什么？

> 业务组件：强绑定业务含义，里面写死业务字段、业务状态，只能本业务域使用； 通用基础组件：和业务无关，通过 props 配置适配不同场景，可以跨多个业务模块复用。

**中控（JeecgBoot/Vue 3）**

1. **通用基础组件**：STable 可拖拽表格、SDrawer 抽屉、SDepartSelect 部门岗位弹窗。不绑定 CRM 业务字段，通过 props 传入 columns、api、主键，多个页面可以复用，属于通用业务基础组件。
2. **业务组件**：SCardShow 仅查看组件，强绑定 CRM 活动记录数据结构，只给市场管理模块使用，属于业务组件。

**君同智能（Vue 3+React）**

1. **Vue 侧业务组件**：virtual‑machine‑card 虚拟机卡片、batch‑operation‑button 批量操作按钮，强绑定虚拟机实训业务状态、字段，只能实验控制台使用，业务组件。
2. **React 侧通用组件**：DocxPreviewWindow、XlsxPreviewWindow 文件预览组件；`useFileUpload` 通用上传 hooks，和企业动态、资源中心业务无关，多个模块都可以调用，属于通用基础组件。

**区分标准总结**

1. 是否硬编码业务字段、业务枚举、业务状态；硬编码业务字段=业务组件；
2. 是否可以通过 props 完全配置，剥离业务数据后还可以给其他页面使用；
3. 使用范围：仅单一业务模块使用，业务组件；跨多个业务模块复用，通用组件。

> 开发经验：优先抽离通用组件；业务组件尽量薄，内部尽量复用通用基础组件，不要把通用逻辑写在业务组件里面。

## 10. 讲一个君同实习印象最深的 BUG，复现、排查、修复，收获？

> 案例：React 资源管理模块，图片上传成功后，上传组件一直显示“图片上传中”转圈状态。

- **复现**：选择图片，调用自定义 customRequest 上传，后端返回成功，但是 ProFormUploadButton 依旧 loading 转圈，不会结束。
- **排查**：查看 Ant Design Pro ProFormUploadButton 文档，customRequest 自定义上传，**必须手动调用 onSuccess 回调**通知组件上传完成。我最开始拿到后端成功结果之后没有调用 e.onSuccess()，组件不知道上传结束，loading 状态不会重置。
- **修复**：拿到后端成功返回，手动调用 `options.onSuccess(responseData)`，通知组件结束 loading。
- **收获**：使用高阶封装组件，不能只看业务效果，要看透组件内部回调契约，自定义覆写逻辑，必须完整走完组件生命周期回调，否则会出现状态异常。

## 2. ESLint + Prettier，两者分别干什么？两者冲突怎么解决？项目中 `.eslintrc`、`.prettierrc` 关键配置你配置哪些？

### 两者职责

- **ESLint**：侧重**代码质量检查**，检测 JS/TS 语法错误、潜在 bug、不规范写法（变量未定义、未使用变量、错误语法），偏向逻辑质量。
- **Prettier**：侧重**代码格式化**，管换行、引号、分号、缩进、行宽，只管样式排版，不管业务逻辑。

**冲突根源**：部分规则两者同时管控，比如引号、分号，ESLint 规则和 Prettier 规则不一致就会报红。

**冲突解决方案**：

1. 安装依赖 `eslint‑config‑prettier`、`eslint‑plugin‑prettier`；
2. 在 eslintrc extends 最后加入 `"plugin:prettier/recommended"`，**让 ESLint 接管 Prettier，把 Prettier 格式问题当做 ESLint 规则，关闭 ESLint 中和格式化冲突的规则**，保证只有一套格式化标准。

### 项目关键配置

1. `.eslintrc`：开启 vue 3、typescript 支持；关闭部分不必要规则；集成 prettier 插件；对 `*.d.ts` 类型文件忽略校验；
2. `.prettierrc`：设置 2 空格缩进，单引号，语句末尾不带分号，设置 printWidth 行宽，html 结束标签换行；
3. vite 配置里面集成 eslint 插件，开发阶段实时提示代码问题；
4. package.json 配置 `lint` 脚本，可以一键修复大部分格式问题。

> 目的：团队代码风格统一，减少格式化 git diff 产生大量无关代码变更。

## 3. Pinia 实现购物车模块，结合 localStorage 做持久化。Pinia 对比 Vuex 优势是什么？state、getters、actions 怎么用？localStorage 持久化，是手写监听存储还是 pinia‑plugin‑persistedstate 插件？如果用插件讲配置；手写的话讲实现思路。页面刷新购物车丢失、多页面状态不一致为什么会发生？你的解决方案。

### Pinia 对比 Vuex 优势

1. **去掉 Mutation**，状态修改直接在 actions 里面写，不需要 mutation 这一层，代码更简洁；
2. **天然模块化**，每个 store 独立，不需要嵌套 modules；TS 类型推导非常友好，类型提示完善；
3. 没有命名空间 namespace 概念；Devtools 调试支持更好；
4. 组合式写法，直接 import 使用 store，不需要 `this.$store`，在 setup 语法糖里面用起来更舒服。

### 购物车 store 结构

- `state(ref)`：购物车商品数组，保存商品 id、skuId、数量、选中状态、价格；
- `getters`：计算属性，统计购物车总数量、选中商品总价格、选中商品列表；
- `actions`：addCart 添加商品、updateCount 修改数量、toggleSelected 单选、toggleAll 全选、deleteCart 删除商品。

### 持久化实现

我项目使用 `pinia‑plugin‑persistedstate` 持久化插件，不是手写监听。 配置步骤：

1. 安装插件；
2. main.ts 中 `createPinia()` 之后 `use(piniaPluginPersistedstate)` 注册全局插件；
3. 在 cart store 定义选项设置 `persist:true`，自动把 state 保存到 localStorage，刷新页面自动从 localStorage 恢复 state 数据。

> 补充：如果手写实现思路：监听 store 状态变化，watch 深度监听 cart 数组，变化就 JSON.stringify 存入 localStorage；store 初始化的时候读取 localStorage 解析赋值给 state。缺点需要自己处理序列化、边界异常，插件更加成熟。

### 问题：页面刷新购物车数据丢失、多页面状态不一致

- **刷新丢失原因**：Pinia 状态保存在内存，浏览器刷新内存全部清空。
- **多页面状态不一致**：不同页面组件各自拷贝一份购物数据，没有统一使用 pinia 响应式 state，组件自己维护副本，修改只改副本，没有调用 store 的 action。

**解决方案**

1. 使用 pinia‑plugin‑persistedstate，内存状态落本地存储，刷新自动恢复；
2. 所有组件**不拷贝解构破坏响应式**，直接使用 store 的 ref 响应式对象；所有增删改操作统一调用 store 里面 action，不直接在组件修改 state；保证全局一份数据源，多页面状态自动同步。

> 注意：不要直接 `const cartList = store.cartList.value` 拿到普通数组，会丢失响应式。

## 4. SKU 规格弹窗组件，讲讲实现逻辑，多规格联动互斥怎么处理？

SKU 就是库存最小销售单元，不同颜色、尺寸对应不同库存、价格。弹窗用来选择商品规格，选择完成把 sku 信息抛给父组件，用于加入购物车。

**实现逻辑**

1. props 接收父组件传入的 sku 规格列表、库存数据；
2. 内部维护选中规格对象，记录用户每一类规格选中的值；
3. 点击规格选项，更新选中对象；
4. **联动互斥逻辑**：
    - 根据已选规格，计算剩下所有可选 sku 组合，过滤出合法可点击规格；
    - 不在合法组合内的规格按钮置灰不可点击；
    - 判断是否**全部规格维度已经选完**，如果全部选完，就匹配到具体 sku，拿到对应库存、价格；
5. 如果用户选择完成，校验库存，通过 `emit('confirm', skuInfo)` 把选中 sku 抛出父组件；取消则 emit 关闭弹窗。

**踩坑**：部分规格组合没有库存，按钮需要置灰；用户重新选择某一项的时候，要清除后续维度已经选中的值，避免出现非法组合。 弹窗用 v‑model 控制显隐，使用 Teleport 把弹窗挂载 body 下，避免父组件 overflow 隐藏导致弹窗被截断。

## 5. IntersectionObserver 实现图片懒加载，原理是什么？对比 scroll 事件监听实现懒加载，两者优缺点？有什么坑点（边界、兼容性）？

### IntersectionObserver 原理

浏览器原生 API，**异步观察目标 DOM 元素和视口的交叉状态**。不需要滚动事件。当图片元素进入视口（即将可见），触发回调函数，把 data‑src 真实图片地址赋值给 src 属性，加载图片；未进入视口只显示占位图。

### 和 scroll 监听对比

|实现方式|优点|缺点|
|---|---|---|
|IntersectionObserver|浏览器异步，主线程开销小，性能好；不用自己计算 offsetTop；支持根容器配置|低版本浏览器需要 polyfill 兼容；元素销毁要手动取消观察|
|scroll 事件监听|兼容性好，老浏览器支持|scroll 高频触发，需要节流；频繁调用 getBoundingClientRect，重排开销大，性能差|

### 坑点

1. **需要取消观察**：组件销毁，必须调用 `observer.unobserve(dom)`，不然内存泄漏；
2. 根元素滚动容器不是 window 的时候，需要配置 root 参数；
3. 兼容性：IE 不支持，需要引入 polyfill 垫片；
4. 如果图片容器一开始 display:none，观察不会触发；
5. 可以设置 rootMargin 提前预加载图片，用户滚动到之前就开始请求图片，提升体验。

> 我项目封装了自定义 composable 钩子，封装图片懒加载逻辑，组件复用。

## 6. 无限滚动分页实现思路，什么时候触发加载下一页？需要做哪些边界处理（loading、无更多数据、重复请求）？

### 实现思路

商品列表页，监听页面触底，触发加载下一页接口；page 页码自增；后端返回的新数组拼接到老列表数组后面渲染。

### 触发时机

滚动容器滚动到底部（距离底部一定阈值，提前加载）就触发加载函数。我这里没有用 ElementPlus 的 `v‑infinite‑scroll` 指令，自己结合 IntersectionObserver：放一个底部哨兵 DOM 元素，哨兵进入视口就加载下一页。

### 边界处理

1. **loading 状态**：请求过程开启 loading，**加锁**，请求未返回前禁止再次触发加载，防止短时间多次触发重复发请求；
2. **无更多数据**：判断后端返回 items 数组长度为 0，设置 finished 标记，不再触发加载；
3. **切换筛选条件**：重置 page=1，清空列表，重置 loading、finished 状态；
4. 组件销毁取消观察者，清理副作用；
5. 接口异常，关闭 loading，提示错误，不锁死页面。

## 1. 这个图书馆系统有哪几种角色？权限控制整体方案是什么？Vue Router 动态路由实现权限控制完整流程。登录拿到角色→后端返回菜单还是前端写死菜单？`addRoute` 使用有什么坑？页面刷新后动态路由丢失怎么解决？

### 角色

系统一共有 5 种身份：**社会人员、学生、老师、普通管理员、系统管理员**。

- 读者三类：社会人员最多借 5 本，借期 15 天；学生最多 20 本，借期 30 天；老师最多 50 本，借期 60 天，各角色续借天数也不一样；
- 普通管理员：图书增删改查、处理归还确认、查看用户列表；
- **系统管理员**：在管理员基础上，可以修改其他用户的角色身份。

### 权限整体方案

采用 **RBAC 基于角色的访问控制模型**。 后端做接口鉴权，每个接口校验当前登录用户角色；前端做**动态路由+菜单控制**，不同角色看到不同侧边栏菜单，防止越权访问。双重校验：**前端只是体验控制，所有接口后端一定再次校验权限，防止直接输 URL 越权。**

### 动态路由完整流程（后端返回菜单）

1. 用户输入账号密码登录，后端校验账号密码，登录成功返回 `token`、用户基本信息、用户角色、该角色可访问的菜单路由列表；
2. 前端把 token 存到 `sessionStorage`，Pinia 用户 store 保存用户信息、角色、原始菜单数组；
3. 拿到后端返回的菜单配置，前端把后端的菜单 JSON 转换成 Vue Router 路由对象；
4. 循环调用 `router.addRoute()` 动态追加路由；
5. 侧边栏根据 store 里面的菜单数组渲染；
6. 配置全局路由守卫 `router.beforeEach`：判断是否有 token，没有跳登录；有 token 判断是否已经加载过动态路由。

> 本项目**菜单由后端返回，不是前端写死路由**，方便后期新增角色直接改数据库，不需要改前端代码。

### addRoute 遇到的坑

1. 页面刷新之后，`addRoute` 添加的路由内存丢失，直接访问页面 404；
2. `addRoute` 是追加路由，如果多次执行（重复登录、守卫多次触发）会重复添加同一份路由，出现路由重复警告；
3. 404 通配路由 `/:pathMatch(.*)*` 不能一开始就写死在 routes 数组，**必须所有动态路由 addRoute 完成之后再 addRoute 添加 404 页面**，否则动态路由还没加载就直接跳 404。

### 刷新动态路由丢失解决方案

1. 浏览器刷新，Pinia 内存数据全部清空，但是 `sessionStorage` 还保留 token；
2. 在路由守卫中：有 token 但是 store 里面菜单数组为空，就主动调用 `getUserInfo()` 接口，重新获取用户信息+菜单；
3. 拿到菜单之后再次执行 `addRoute` 注册动态路由；
4. 处理完动态路由之后，使用 `next(to.fullPath)` 重新放行当前页面，不能直接 next()。
5. 增加标记变量 `isAddRoutes`，避免守卫循环重复执行 addRoute。

## 2. Axios 请求拦截器、响应拦截器你封装了哪些逻辑？token 过期如何处理？

我基于 axios 封装统一请求实例。 **请求拦截器（request interceptor）**

1. 从 sessionStorage 读取 token，放到请求头 `Authorization`；
2. post 请求统一处理请求头 `Content‑Type`；
3. 对部分接口可以增加 loading 状态标记。

**响应拦截器（response interceptor）**

1. 解构后端返回统一 Result 封装，剥离外层 code/message，直接返回业务 result 数据给业务页面；
2. **错误码统一处理**：
    - 401：token 过期 / token 无效；清空 pinia 用户状态、清空 sessionStorage，弹窗提示，跳转到登录页；
    - 403：没有权限，提示无权限访问；
    - 500：后端服务异常，弹出 toast 提示服务器内部错误；
    - 业务自定义错误码，直接抛出错误给业务 catch 捕获。
3. 网络超时、断网捕获，给出友好提示。

> 注意：登录失败 5 次账号会被后端冻结 60 分钟，这个业务逻辑完全在后端实现，前端只负责接收后端返回的冻结提示文案展示给用户。

## 3. 路由‑面包屑‑Tab 栏三者联动缓存，你的实现思路？Tab 栏缓存页面状态是否用 keep‑alive？讲讲 keep‑alive 原理、include/exclude。页面关闭 Tab，怎么清除缓存？

### 整体联动思路

1. **路由变化是数据源源头**。路由守卫监听 `$route` 变化；
2. 面包屑：读取当前 route 的 `meta.title`、meta 上级层级，递归生成面包屑数组；
3. Tab 栏：维护一个 pinia 的 tabStore，数组保存已经打开的 tab 对象{path, title}；路由切换时，如果 tab 数组没有当前路由，就 push 进去；
4. 点击 Tab 标签直接 `router.push(tab.path)`；关闭 Tab 的时候删除 store 数组对应项。

### keep‑alive 页面缓存

使用 `<keep‑alive :include="cachedViews">` 实现页面组件状态缓存，比如图书列表页面，切换 tab 回来，保留搜索条件、页码，不用重新请求接口。

- `include`：数组，存放组件 name，只有名字在数组里面才会被缓存；
- `exclude`：数组，匹配到 name 就不会缓存；
- keep‑alive 原理：是 Vue 内置抽象组件，不会生成 DOM；内部维护一个缓存对象 Map，key 是组件 name；组件切换走 `activated / deactivated` 钩子，而不是 onMounted / onUnmounted。

**关闭 Tab 清除缓存：**

1. 关闭 tab 的时候，从 pinia 的 `cachedViews` 数组中移除该页面的组件 name；
2. keep‑alive 的 include 绑定的就是这个数组；数组删除对应 name，该组件缓存就会被销毁。
    
    > 注意：部分页面不需要缓存，例如新增/编辑书籍弹窗页面，组件 name 不加入 cachedViews。
    

## 4. ECharts 图表遇到缩放显示不全，什么场景出现？你的修复方案。

### Q 1：讲一个这个项目印象最深的 BUG？

> 答：**动态路由刷新 404**。 现象：登录进入系统正常，F 5 浏览器刷新页面直接跳 404 页面。 排查：动态路由是代码运行时 `addRoute` 添加，只存在内存，刷新 VueRouter 实例重建，动态路由全部丢失；404 通配路由写死在初始 routes 数组，刷新之后先匹配 404。 修复：路由守卫增加 token 判断，有 token 但没有菜单，重新调用获取用户信息接口，拿到菜单再次 addRoute；**404 通配路由必须等所有动态路由注册完成之后再 addRoute 追加进去**；增加标记变量防止守卫循环。

### Q 2：项目里面消息通知怎么实现？

### Q 3：如果有多个用户同时借阅同一本仅剩 1 本的图书，如何防止超借？

## 1. TypeScript：项目大量使用 TS，说说 interface 和 type 区别；泛型使用场景，举你项目里使用泛型例子；as 类型断言什么时候用，有什么风险。

### interface 和 type 的区别

1. **interface 主要用来描述对象、类的结构；type 是类型别名，可以描述对象、基础类型、联合、交叉类型、元组**。

- interface 只能定义对象/类结构，不能直接写 `type A = number | string` 这种联合类型；

1. **interface 支持声明合并，type 不支持**：同一个 interface 多次声明会自动合并属性；type 重复定义直接报错；

```
interface User { name:string }
interface User { age:number } 
// 自动合并为 {name:string,age:number}
```

3. 继承写法不一样：interface 用 `extends`；type 对象交叉使用 `&` 交叉运算符。
4. 日常开发：**描述对象实体、后端返回数据结构优先用 interface；联合、元组、工具类型优先用 type**。

### 泛型使用场景

> 泛型就是**类型参数化**，组件/函数不写死类型，调用的时候再传入具体类型，实现类型复用、保留类型推导。 适用场景：通用工具函数、通用组件、通用网络请求封装。

**我的项目实际例子**

1. 中控实习：封装 axios 请求函数，写通用 `request<T>`，传入响应体类型 T，请求返回 Promise。不管是查用户、查图书，传入不同 interface，ts 自动推导出返回数据类型。

```
function request<T>(url:string,config:AxiosRequestConfig):Promise<T>{
  return axios.get(url,config).then(res=>res.data as T)
}
// 使用：查询图书
interface BookItem { bookId:number; title:string }
const book = await request<BookItem>("/api/book/list")
```

2. 小兔鲜电商、图书馆项目，封装通用分页返回泛型：`PageResult<T>`，`T` 代表列表项类型，分页统一结构：`{records:T[],total:number,pageNum:number}`，不同业务传入不同实体。

### as 类型断言

> 作用：告诉 TS“我比类型检查更清楚这个变量是什么类型”，强制把变量转为指定类型。 **使用时机**：

1. TS 推导类型不准确，确定实际类型和编译推导不一致；
2. 获取 DOM 元素，`document.getElementById('xxx')` 返回 `HTMLElement|null`，我确定 DOM 一定存在，`const dom = document.getElementById('box') as HTMLDivElement`。

**风险**： `as` 只是编译阶段欺骗 TS，**不会做运行时类型校验**。如果实际运行数据和断言类型不一致，编译不会报错，运行直接出现属性 undefined、调用方法报错。

> 注意：不要滥用 as，优先用类型守卫 `typeof、instanceof` 做运行时判断，而不是直接 as 强制转换。

## 2. Vue 3 相关：说说组合式 API 对比选项式 API；setup 执行时机；ref、reactive 区别；说说 Vue 3 响应式原理 Proxy，对比 Vue 2 Object.defineProperty 的缺陷。

### 组合式 API vs 选项式 API

1. **选项式（OptionsAPI）**：data、methods、computed、watch 分散在不同选项；简单页面写起来简单；但复杂组件，同一业务逻辑被拆分到不同选项，业务逻辑分散，复用逻辑困难。
2. **组合式 API（CompositionAPI）**：相关的状态、方法、计算、watch 写在一起，按业务功能聚合代码；
    - 更好逻辑复用：抽成 composables 自定义 hooks，我小兔鲜、中控实习都大量抽离 hooks；
    - TS 类型推导更友好；
    - 缺点：上手有学习成本，需要自己管理响应式。

> `<script setup>` 是语法糖，简化组合式 API，不需要 return，模板直接使用顶层变量，是现在项目主流写法。

### setup 执行时机

`setup` 是 **beforeCreate 之前执行**，组件实例还没有创建，`this` 是 `undefined`，不能访问 `this.$data、this.$methods`。

> script‑setup 语法糖本质就是编译时的语法糖，底层还是 setup 函数。

### ref、reactive 区别

1. `reactive`：**仅支持对象/数组引用类型**，不能处理基础类型（string number boolean）；返回原对象代理；直接解构会丢失响应式。
2. `ref`：既支持**基础类型，也支持对象**；底层如果传对象内部会自动调用 reactive；返回一个包装对象，值存在 `.value`；模板中使用会自动解包不需要写.value。

> 开发习惯：简单基础数据用 ref；复杂对象用 reactive；解构 reactive 要用 `toRefs/toRef` 保留响应式。

### Vue 3 Proxy 响应式原理 & Vue 2 defineProperty 缺陷

Vue 3 使用 **Proxy** 代理整个对象，拦截对象的读取、修改、删除、新增属性；配合 Reflect 做反射操作。

Vue 2 `Object.defineProperty` 缺陷：

1. **无法监听对象新增、删除属性**，需要 `Vue.set / this.$set`；
2. **无法监听数组下标修改、数组长度修改**；需要重写数组 7 个方法实现劫持；
3. 只能劫持对象已有的属性；
4. 只能劫持单个属性，需要递归遍历整个对象所有属性；

Proxy 优势：

1. 代理整个对象，拦截新增、删除属性；
2. 原生支持数组下标、length 修改监听；
3. 不需要一开始递归全部，支持惰性代理；
    
    > 局限：Proxy 不支持 IE 浏览器。

## 3. React：简历写掌握 React，讲讲 useState、useEffect 依赖数组常见踩坑；useMemo、useCallback 使用场景，什么情况不要滥用。

### useState、useEffect 踩坑

1. **useState 是异步更新**：setState 修改状态不会立刻拿到最新 state，同一函数内多次 setState 会合并。
2. 闭包陷阱：`useEffect` 捕获渲染闭包，effect 内部拿到的 state 是创建那一次的旧快照，不是最新值；根源来自**依赖数组缺失**。
3. **依赖数组漏写**：effect 用到的 state、函数，没有写到依赖数组里面，拿到旧值，逻辑异常；写多了又会造成 effect 无意义重复执行。
4. 对象/数组作为依赖：引用类型直接放依赖数组，每次渲染生成新引用，effect 重复触发；可以 useMemo 缓存对象。
5. useEffect 清理函数：副作用定时器、事件监听，需要返回清理函数；组件销毁不清理造成内存泄漏（君同实习项目遇到过）。

### useMemo、useCallback

- `useMemo`：缓存**计算结果值**；避免每次重渲染重复执行高开销计算函数。
- `useCallback`：缓存**函数引用**，缓存函数实例，避免每次渲染生成新函数，主要用于传给子组件，配合 `React.memo` 做组件记忆。

**使用场景**

1. useMemo：组件渲染有很耗 CPU 的计算（大数据过滤、排序）；
2. useCallback：把回调传给被 `React.memo` 包裹的子组件，防止子组件无意义重复渲染。

**不要滥用的情况**

1. 简单计算不要用 useMemo，本身缓存也有性能开销；
2. 子组件没有用 `React.memo`，那 useCallback 完全没有收益，白白增加开销；
    
    > 很多人盲目全部加 useMemo/useCallback，反而增加内存，要做性能瓶颈确认之后再优化，不要提前优化。

## 4. 浏览器相关：浏览器渲染流程，重排重绘；浏览器缓存（强缓存、协商缓存）详细讲；跨域有哪些解决方案，CORS 简单原理。

### 浏览器渲染完整流程

1. HTML 解析生成 DOM 树；CSS 解析生成 CSSOM 样式树；
2. DOM + CSSOM 合并生成 **Render Tree 渲染树**（只包含可见节点）；
3. **Layout 布局（重排 reflow）**：计算每个元素几何位置、大小；
4. **Paint 绘制（重绘 repaint）**：按照布局信息填充像素、颜色、图片到图层；
5. Composite 合成：多个图层 GPU 合成，输出屏幕。

- **重排(reflow)**：元素**几何尺寸、位置改变**，重新 Layout 布局；开销大。
- **重绘(repaint)**：仅仅改变颜色、背景色，不改变布局，跳过 Layout，直接 Paint，开销比重排小。
    
    > 触发重排：修改宽高、margin、offsetTop，DOM 增删； 优化：批量修改 DOM，文档碎片、脱离文档流、使用 transform，transform 走合成层，不会触发重排重绘。
    

### 浏览器 HTTP 缓存（强缓存 + 协商缓存）

#### ①强缓存：不用发请求，直接读取本地磁盘/内存，状态码 200(from disk cache / memory cache)

响应头：

- `Expires`：http 1.0，绝对时间；客户端时间不准会失效；
- `Cache‑Control: max‑age=xxx` http 1.1，相对时间秒数，优先级高于 Expires。

max‑age 时间没过期，直接本地拿，**不跟服务器通信**。

#### ②协商缓存：强缓存失效，浏览器发请求到服务器，服务器判断资源是否没变

两组头，优先第二组 ETag：

1. `Last‑Modified`：服务器返回文件最后修改时间；下次请求带上 `If‑Modified‑Since`；
2. `ETag`：资源唯一哈希标识；下次请求头带上 `If‑None‑Match`；

服务器对比：

- 资源未变化：返回 `304 Not Modified`，浏览器继续用本地缓存；
- 资源变化：返回 200，返回全新资源，更新缓存。

> 优先级：Cache‑Control > Expires；ETag > Last‑Modified。

### 跨域：浏览器同源策略限制，协议、域名、端口任意一个不一样就是跨域。

**常见解决方案**

1. 开发环境：**前端构建工具代理**（Vite/Webpack devServer proxy）；
2. 生产：**CORS 后端配置跨域**（最主流）；
3. Nginx 反向代理；
4. JSONP（仅 GET，不推荐）；
5. postMessage（不同窗口 iframe 通信）。

**CORS 简单原理** 后端服务器设置响应头，告诉浏览器允许哪些源访问。 简单请求直接返回 CORS 响应头； 非简单请求（PUT、DELETE、带自定义 header、content‑type 不是表单），浏览器**先发 OPTIONS 预检请求**，询问服务器是否允许跨域；预检通过，才发真实业务请求。

> 关键点：跨域限制是浏览器的安全策略，**不是服务器拒绝接收请求，请求已经到达后端，浏览器拦截了返回结果**。

## 5. 前端工程化：Vite 相比 Webpack 的优势，Vite 的实现原理。

### Webpack 问题

开发环境全部文件打包构建，把所有模块打包到 bundle，项目越大，冷启动越慢；全部走 JS 打包编译。

### Vite 原理

分为**开发环境**和**生产环境**两套完全不同策略

1. **开发环境：基于浏览器原生 ES Module**

- 启动不打包全部代码；用 esbuild 预构建第三方依赖（node_modules），转为浏览器可识别的 esm；
- 浏览器发起 http 请求按需请求模块；浏览器本身做模块解析；
- 热更新 HMR：只更新变更模块，和项目大小几乎无关；**冷启动极快**。

1. **生产环境：使用 Rollup 打包**
    
    > 浏览器原生 ESM 不适合生产，有网络碎片请求问题；生产使用 Rollup 做完整打包、代码分割、压缩。
    

### Vite 对比 Webpack 优势

1. 开发环境冷启动速度快，不受项目体积影响；
2. HMR 热更新性能好，修改文件只更新变更模块；
3. esbuild 预构建，使用 Go 编写，编译速度远快于 JS 写的 webpack；
4. 开箱即用 TS、Sass，配置简洁。

> 缺点：部分老的 CommonJS 库兼容性问题，需要 esbuild 预构建做转换。

## 6. 组件封装：封装通用组件，你会考虑哪些点？props 校验、类型约束、事件、插槽、边界异常处理。

结合我中控实习封装 `STable、SDrawer`、君同的文件预览组件，封装通用组件考虑：

1. **Props：类型约束+校验**
    - TS 定义 interface 做 props 类型；Vue 3 可以用 `withDefaults` 设置默认值；
    - 区分必传/可选参数；功能开关布尔属性；不要传大量耦合业务字段。
2. **单向数据流原则**：组件内部不要直接修改 props，事件 emit 通知父组件修改数据。
3. **事件 emit**：对外事件明确语义；ts 约束 emit 事件参数类型；提供 change、confirm、close 等事件；
4. **插槽 slots**：默认插槽、具名插槽、作用域插槽；区分默认内容，父不传入插槽有兜底 UI；允许业务覆盖部分 UI，兼顾通用性和业务定制。
5. **实例暴露方法(defineExpose)**：对外暴露 ref 可调用的方法，例如抽屉 `reset()`、表格 `clear()`，我 SDrawer、STable 都暴露实例方法。
6. **边界异常处理**
    - 空数据、传入 undefined/null 的兜底渲染；
    - 加载 loading 状态、异常错误兜底页面；
    - 组件销毁清除定时器、监听、取消请求，防止内存泄漏；
7. **样式处理**：scoped + :deep，预留外部自定义 class 类名，允许父组件覆盖样式；
8. **复用性：剥离业务硬编码**，业务字段不要写死组件内部，全部由 props 传入；
9. 文档注释：每个 props、emit 写注释，方便团队使用。

## 7. 简单场景题

### 1）父组件大量数据传给子组件，子组件频繁触发渲染，如何做优化？

1. **Vue 3 场景**
    - 如果对象 props，不要在子组件解构，避免丢失响应式；
    - 子组件使用 `defineOptions({ inheritAttrs:false })`；避免无关 attribute 继承；
    - 子组件计算属性 computed，把复杂计算放到 computed；
    - 大列表场景使用虚拟列表，减少 DOM 节点；
    - 避免 props 传递庞大完整对象，尽量只传需要的字段。
2. **React 场景**
    - 子组件包 `React.memo` 做浅层比较；
    - 传给子组件的回调函数使用 `useCallback`；复杂派生数据 `useMemo` 缓存；
3. 通用：
    - 确认是否真的需要频繁渲染，排查是否有不必要状态变更；
    - 把不依赖变化数据的部分拆成独立子组件，隔离渲染范围；
    - 大数据不要完整透传，尽量按需分片。

### 2）如果一个后台管理系统页面接口很多，页面加载慢，从前端角度可以从哪些方向排查优化？

**第一步：定位瓶颈，看 Network 面板** 看是接口慢？还是 DOM 渲染慢？还是打包资源体积大？

1. **接口请求层面**
    - 多个独立接口：能合并的接口后端合并；不能合并看是否可以并行请求；避免串行 await；
    - 不需要页面初始化立刻展示的数据，**延迟请求、按需请求**（tab 切换之后才请求对应 tab 接口，不要页面一打开全部请求）；
    - 接口做缓存，相同请求避免重复调用；
    - 分页，大数据不分页一次性返回会接口慢+渲染卡顿。
2. **资源与打包**
    - 路由懒加载，拆分 chunk，首屏不要加载全部页面代码；
    - 大第三方库按需导入，排除大体积依赖；
3. **渲染层面**
    - 大量表格列表：虚拟列表，减少 DOM 节点；
    - 避免模板大量复杂表达式，使用 computed；
    - ECharts、大组件延迟渲染；keep‑alive 合理使用；
4. **缓存策略**
    - 静态资源开启浏览器缓存；接口合适场景做本地缓存；
5. **体验优化**
    - 增加骨架屏、loading，避免空白；错误兜底；
6. 排查内存：检查是否存在未销毁定时器、事件监听。

> 补充：如果是后端接口本身响应慢，前端只能做体验优化，根本需要后端优化 SQL、索引。

## 4. 你写了很多组件封装，那如果让你开发一个公司内部前端组件库，你会考虑哪些方面？

结合我实习封装业务组件的经验，如果做公司内部组件库，和业务组件不一样，要兼顾通用性、稳定性、可维护性、团队使用体验，主要考虑这几块：

1. **技术选型与工程化底座** 确定技术栈（Vue 3 还是 React，TS 强制类型）；搭建组件库工程，使用 Vite 或者 Rollup 做构建；支持 ESM、CommonJS 两种产物；配置 eslint+prettier 统一代码规范；单元测试环境 Jest/Vitest。
2. **组件设计原则** 遵循单一职责；剥离业务硬编码，不要写死业务字段；props、emit 完整 TS 类型约束；支持插槽、作用域插槽；对外暴露必要实例方法；做好边界兼容：空数据、异常、loading、错误状态。严格单向数据流，组件不直接修改 props。
3. **样式方案** 确定样式策略：CSS‑Variables 变量定制主题，方便公司主题切换；支持 scss 变量；支持组件 className 属性，允许业务层自定义覆盖样式；避免样式污染。
4. **文档与示例** 组件库必须配套文档网站，每个组件提供示例、props、事件、插槽说明，使用注意事项；提供复制代码示例，降低团队接入成本。
5. **版本管理** 语义化版本号；变更日志 CHANGELOG；区分 breaking change，大版本升级提示；内部 npm 私有源发布。
6. **质量保障** 单元测试覆盖核心逻辑；组件 Demo 回归测试；处理浏览器兼容性；
7. **迭代机制** 收集业务团队反馈；区分通用能力和业务能力，业务组件不放进基础组件库；定期迭代，避免组件库无限膨胀。

> 补充：业务中大量重复的业务组件，不应该放到基础组件库；基础组件库只放与业务无关的通用能力。
